4  Arquitectura del workspace

El workspace de Thalos está organizado en cuatro crates dentro de un workspace Cargo.

backend/
├── Cargo.toml                    # workspace root
├── crates/
│   ├── thalos-core/              # Núcleo matemático-robótico
│   ├── thalos-visual/            # Representación visual
│   ├── thalos-runtime/           # 🆕 Orquestación runtime
│   └── thalos-api/               # Exposición externa (HTTP)

4.1 thalos-core

Responsabilidad: Núcleo matemático y robótico del sistema. Es el crate fundacional — todo lo demás depende de él.

No depende de: nada externo excepto nalgebra y thiserror.

4.1.1 Estructura interna

thalos-core/src/
├── lib.rs                        # Punto de entrada, declara módulos públicos
├── prelude.rs                    # Re-exportaciones convenientes
├── math/                         # Infraestructura matemática reutilizable
│   ├── geometry/
│   │   ├── vectors/              # Vector3, UnitVector3
│   │   ├── rotations/            # Quaternion, UnitQuaternion
│   │   └── rigid/                # Transform3D, Transform<From,To>
│   ├── algebra/                  # DynamicMatrix (alias DMatrix)
│   ├── traits/                   # Cross, Dot (traits para productos)
│   ├── constants.rs              # EPS, PI, JACOBIAN_EPS, DEG_TO_RAD
│   └── error.rs                  # MathError
├── robot/                        # Representación estructural de robots
│   ├── joint/                    # JointType, RevoluteJoint, PrismaticJoint
│   ├── link.rs                   # Link (id + transform)
│   ├── segment.rs                # Segment (parent + child + joint + link)
│   ├── serial_chain.rs           # SerialChain (segments + frames + end_effector)
│   ├── builder.rs                # SerialChainBuilder
│   └── error.rs                  # RobotBuilderError
├── kinematics/                   # Cálculos cinemáticos
│   ├── forward/                  # ForwardKinematics, FKResult
│   └── jacobian/                 # Jacobian, GeometricJacobian, NumericalJacobian
├── spatial/                      # Representación espacial y frames
│   ├── frame/                    # FrameId, Frame, FrameRegistry, FrameGraph
│   └── pose.rs                   # Pose (reference + target + transform)
└── models/                       # Implementaciones de robots concretos
    ├── single_revolute/          # Robot de 1 joint rotacional
    ├── planar_2r/                # Robot planar de 2 revoluciones
    ├── planar_3r/                # Robot planar de 3 revoluciones
    ├── scara/                    # Robot SCARA (4 DOF)
    ├── factory.rs                # RobotRegistry, RobotModel enum, RobotSpec enum
    └── error.rs                  # RobotRegistryError

4.1.2 Submódulos clave

4.1.2.1 math::geometry::vectors

Define Vector3 y UnitVector3. Operaciones: suma, resta, multiplicación por escalar, magnitud, normalización (con error si zero).

4.1.2.2 math::geometry::rotations

Define Quaternion (modelo algebraico puro) y UnitQuaternion (rotaciones SO(3) con invariante de norma). UnitQuaternion::new() valida la norma; from_axis_angle() y from_euler() construyen garantizando norma = 1.

4.1.2.3 math::geometry::rigid

Define Transform3D (traslación + rotación) con compose(). También Transform<From, To> con PhantomData para type safety entre frames.

4.1.2.4 robot::serial_chain

SerialChain es la estructura central del dominio robótico. Contiene: - segments: Vec<Segment> — secuencia ordenada de segmentos - frames: FrameRegistry — registro de todos los frames - end_effector: FrameId — identifica el frame terminal

4.1.2.5 robot::builder

SerialChainBuilder es el constructor con validación. Verifica que todos los frames referenciados por los segments existan en el registry antes de construir.

4.1.2.6 kinematics::forward

ForwardKinematics::evaluate(q) recorre los segments secuencialmente, componiendo transforms: t = t ∘ joint.origin ∘ joint.motion(qⱼ) ∘ link.transform. Devuelve FKResult con poses globales de cada frame.

4.1.2.7 kinematics::jacobian

Dos implementaciones del trait JacobianSolver: - GeometricJacobian — analítico, usa producto cruz zᵢ × (pₑ − pᵢ) - NumericalJacobian — diferencias finitas centrales, (f(q+ε) − f(q−ε)) / 2ε

4.1.2.8 spatial::frame

  • FrameId: enum con World y Id(u64) — identificador único de frame
  • Frame: metadatos (id, name)
  • FrameRegistry: mapa HashMap<FrameId, Frame> con creación auto-incremental
  • FrameGraph: grafo de relaciones entre frames (esqueleto inicial)

4.1.2.9 models

Catálogo de robots concretos con fábricas. RobotRegistry::create(model, spec) valida que el RobotSpec coincida con el RobotModel esperado.

4.1.3 Jerarquía de tipos

FrameId (World | Id(u64))
    │
Frame { id, name }
    │
FrameRegistry { map<FrameId, Frame> }
    │
    ├── SerialChain { segments, frames, end_effector }
    │       │
    │       ├── Segment { parent, child, joint, link }
    │       │               │              │
    │       │               │              └── Link { id, transform }
    │       │               │
    │       │               └── JointType
    │       │                   ├── Revolute { id, axis, limits, origin }
    │       │                   └── Prismatic { id, direction, limits, origin }
    │       │
    │       └── ForwardKinematics.evaluate(q) → FKResult { poses: Map<FrameId, Pose> }
    │
    └── Pose { reference, target, transform }

4.2 thalos-visual

Responsabilidad: Representación y validación visual desacoplada del núcleo matemático.

Depende de: thalos-core, serde.

thalos-visual/src/
├── lib.rs               # Punto de entrada
├── scene/
│   ├── mod.rs           # VisualScene, VisualFrame, VisualLink, VisualJointAxis, VisualTwist
│   ├── precision.rs     # VisualPrecision (normalización numérica)
│   └── diff.rs          # SceneDiff, ChangedFrame
├── builder.rs           # SceneBuilder (FKResult → VisualScene)
├── validator.rs         # SceneValidator (valida invariantes visuales)
└── utils.rs             # clean() — utilidad de limpieza numérica

4.2.1 VisualScene

pub struct VisualScene {
    pub frames: Vec<VisualFrame>,         // frames con id, parent, translation, rotation
    pub links: Vec<VisualLink>,           // segmentos visuales (start → end)
    pub joint_axes: Vec<VisualJointAxis>, // ejes de joints (origin + direction)
    pub twists: Vec<VisualTwist>,         // twists jacobianos (origin + linear + angular)
}

Todas las coordenadas usan [f64; 3] o [f64; 4] — sin tipos del core. Es una representación serializable (derive Serialize, Deserialize).

4.2.2 SceneValidator

Valida 8 invariantes de una escena:

  1. World frame existe — debe haber un frame con id "world"
  2. IDs únicos — sin duplicados
  3. Parents existen — todo parent reference a un frame existente
  4. Sin ciclos — el grafo parent→child no debe tener loops
  5. Conectividad — todos los frames son alcanzables desde "world"
  6. Valores finitos — sin NaN o Infinity
  7. Norma de quaternions — ‖rot‖ ≈ 1
  8. Links consistentes — cada link coincide con la geometría esperada

4.2.3 SceneDiff

SceneDiff::between(old, new, epsilon) detecta frames agregados, eliminados y modificados (con delta de traslación y ángulo de rotación geodésico).

4.2.4 Primitivas geométricas

VisualScene ahora incluye primitives: Vec<VisualPrimitive> para representar objetos 3D con volumen (cilindros, esferas, cajas) que complementan los frames y links. Cada primitiva tiene id, translation, rotation y geometry.

Esto permite modelar elementos visuales concretos como la base column del SCARA, los cuerpos de los links, o marcadores TCP, sin modificar el core.

4.2.5 FrameStyle

FrameStyle permite personalizar el aspecto visual de cada frame individual:

pub struct FrameStyle {
    pub axis_length: f64,     // longitud de cada eje
    pub axis_radius: f64,     // radio del cilindro del eje (0 = línea)
    pub origin_radius: f64,   // radio de la esfera del origen
    pub show_labels: bool,    // etiquetas X/Y/Z
    pub color_x: [f64; 3],    // color RGB del eje X
    pub color_y: [f64; 3],    // color RGB del eje Y
    pub color_z: [f64; 3],    // color RGB del eje Z
}

VisualFrame.style es Option<FrameStyle> — si es None, el frontend usa sus valores por defecto.

4.2.6 Builders específicos por robot

Además de SceneBuilder (genérico), existen builders específicos:

  • ScaraVisualBuilder — genera primitivas geométricas para el SCARA: base_column, link_1_body y link_2_body como cilindros posicionados dinámicamente según la FK actual.

Helpers geométricos: cylinder_between(from, to, radius) crea un cilindro entre dos puntos 3D; align_y_to(direction) produce el quaternion que alinea el eje Y con la dirección dada.

4.3 thalos-runtime

Responsabilidad: Orquestación del estado mutable del sistema — el “cerebro” que conecta el análisis cinemático con la visualización.

Depende de: thalos-core, thalos-visual, thiserror, chrono.

Posición arquitectónica: se encuentra entre thalos-visual y thalos-api. La API consume el runtime, no llama al core ni al visual directamente.

thalos-runtime/src/
├── lib.rs               # Re-exportaciones públicas
├── error.rs             # RuntimeError (Scene + RobotModel)
├── commands/
│   └── mod.rs           # Command enum: SetJoints, LoadRobot
├── state/
│   ├── mod.rs
│   └── robot.rs         # SceneRuntime, ActiveRobot
├── services/
│   ├── mod.rs
│   └── scene.rs         # SceneService (orquestador principal)
├── backends/
│   ├── mod.rs           # RobotBackend trait
│   └── internal.rs      # InternalBackend (catálogo built-in)
└── snapshots/
    ├── mod.rs
    └── scene.rs         # RuntimeSnapshot (point-in-time state)

4.3.1 SceneService

SceneService es el orquestador central. Mantiene el estado mutable (SceneRuntime envuelto en RwLock) y expone dos operaciones principales:

impl SceneService {
    /// Snapshot del estado actual (FK + visual scene).
    pub fn snapshot(&self) -> Result<RuntimeSnapshot, RuntimeError>;

    /// Aplica un comando y devuelve el snapshot resultante.
    pub fn execute(&self, cmd: Command) -> Result<RuntimeSnapshot, RuntimeError>;
}

Cada execute(): 1. Aplica la mutación (setear joints o cargar robot) 2. Corre FK sobre el nuevo estado 3. Construye la escena visual (con el builder correspondiente al modelo) 4. Valida la escena con SceneValidator 5. Devuelve RuntimeSnapshot con todo el estado + timestamp

4.3.2 Command pattern

Las mutaciones están tipadas como Command:

pub enum Command {
    SetJoints(Vec<f64>),   // ángulos articulares
    LoadRobot(String),     // ID del modelo a cargar
}

Esto permite que SceneService::execute() sea un punto único de entrada para toda mutación, facilitando auditoría, logging y futuros undo/redo.

4.3.3 State

SceneRuntime y ActiveRobot modelan el estado mutable:

pub struct SceneRuntime {
    pub active_robot: ActiveRobot,
}

pub struct ActiveRobot {
    pub model: RobotModel,
    pub chain: SerialChain,
    pub joints: Vec<f64>,
}

4.3.4 RobotBackend (trait)

Strategy para resolución de modelos robóticos:

pub trait RobotBackend: Send + Sync {
    fn resolve_model(&id: &str) -> Result<RobotModel, RuntimeError>;
}

InternalBackend resuelve contra el catálogo built-in de thalos-core. Se pueden implementar backends personalizados (hardware, archivos, red).

4.3.5 RuntimeSnapshot

Valor de retorno unificado: contiene el modelo activo, los joints actuales, la escena visual validada y un timestamp.

pub struct RuntimeSnapshot {
    pub robot: RobotModel,
    pub joints: Vec<f64>,
    pub scene: VisualScene,
    pub generated_at: DateTime<Utc>,
}

La API convierte esto a RuntimeStateResponse (DTO HTTP) con From.

4.4.1 Endpoints

Método Ruta Descripción
GET /api/v1/scene Snapshot del runtime actual
POST /api/v1/scene/joints Mutar joints (SetJoints)
POST /api/v1/scene/robot Cargar otro robot (LoadRobot)
POST /api/v1/scene/validate Validar una escena arbitraria
POST /api/v1/scene/diff Diff entre dos escenas
GET /api/v1/robots Listar catálogo de robots
GET /api/v1/robots/{id} Obtener metadata de un robot

Los handlers de scene no contienen lógica de dominio: delegan en thalos_runtime::SceneService::execute(). La API solo traduce HTTP ↔︎ Command.

El frontend está organizado por features (scene, robots), cada uno con sus propios stores, servicios, tipos y componentes. Usa Angular Signals como mecanismo principal de reactividad, con RxJS subyacente para comunicación HTTP y pipelines asíncronos.

4.6.1 Arquitectura del store (SceneStore)

Dos pipelines RxJS paralelos se merged con merge() + scan() para producir un Observable<SceneState> que se convierte en Signal<SceneState> vía toSignal():

qSubject (BehaviorSubject) ─→ auditTime(16) ─→ switchMap → API setJoints ──┐
                                                                           ├→ merge → scan → toSignal → Signal<SceneState>
loadRobotSubject (Subject) ─────────────────→ switchMap → API loadRobot ───┘

Los componentes consumen SceneStore.state como signal. No hay subscriptions manuales — usan effect() o computed().

4.6.2 ThreeRendererService

Renderiza SceneData en Three.js. Soporta:

  • Frames con FrameStyle (esferas de origen, ejes con flechas cónicas)
  • Links como cilindros entre dos puntos
  • Primitivas geométricas (cilindros, esferas, cajas con color por ID)
  • Brújula 3D en esquina (contra-rotada a la cámara para orientación global)

Rotación: Rust serializa quaternions como [w, x, y, z] → Three.js espera (x, y, z, w). El adapter y el renderer aplican esta conversión.
