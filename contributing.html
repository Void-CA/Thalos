9  Contribución a Thalos

Esta guía asume que ya leíste las secciones de arquitectura (Chapter 3) y dominio (Chapter 6). Este documento cubre cómo contribuir de forma efectiva y consistente.

9.1 Convenciones generales

  • Idioma del código: inglés (nombres de tipos, funciones, tests, mensajes de error)
  • Idioma de la documentación: español (este libro)
  • Commits: conventional commits (feat:, fix:, refactor:, docs:, test:)
  • Formato: cargo fmt antes de cada commit
  • Lints: cargo clippy sin warnings

9.2 Estructura esperada por crate

9.2.1 thalos-core

crates/thalos-core/src/
├── lib.rs            # Declaración de módulos públicos
├── prelude.rs        # Re-exportaciones convenientes (opcional)
├── <mod>/
│   ├── mod.rs        # Declaración de submódulos + re-exportaciones
│   ├── <type>.rs     # Un tipo por archivo (preferentemente)
│   └── ...           # Archivos de soporte

Reglas:

  • Un tipo principal por archivo. RevoluteJoint va en revolute.rs, no en joint.rs junto con PrismaticJoint.
  • Los enums unificadores (como JointType) van en el archivo que lleva el nombre del concepto (joint.rs).
  • Los tests unitarios van al final del archivo que testean, en un módulo #[cfg(test)] mod <type>_tests { ... }.
  • Las fábricas de modelos concretos van en models/<name>/factory.rs.

9.2.2 thalos-visual

crates/thalos-visual/src/
├── lib.rs            # Re-exportaciones públicas
├── scene/
│   ├── mod.rs        # VisualScene, VisualFrame, VisualPrimitive, FrameStyle, etc.
│   ├── precision.rs  # VisualPrecision (normalización numérica)
│   └── diff.rs       # SceneDiff, ChangedFrame
├── builder.rs        # SceneBuilder (FK → VisualScene) + helpers (cylinder_between, align_y_to)
├── scara.rs          # ScaraVisualBuilder (builders específicos por robot)
├── validator.rs      # SceneValidator (invariantes)
└── utils.rs          # Utilidades pequeñas
  • Los tipos visuales se declaran en scene/mod.rs con derive(Serialize, Deserialize).
  • SceneBuilder importa del core pero no modifica estructuras del core.
  • SceneValidator es autónomo: solo recibe un &VisualScene y devuelve Result<(), SceneError>.
  • Los builders específicos (ej: ScaraVisualBuilder) van en archivos separados y extienden SceneBuilder para generar primitivas geométricas.
  • Los helpers geométricos (cylinder_between, align_y_to) viven en builder.rs y se exportan para reuso.

9.2.3 thalos-runtime

crates/thalos-runtime/src/
├── lib.rs            # Re-exportaciones públicas
├── error.rs          # RuntimeError
├── commands/
│   └── mod.rs        # Command enum (SetJoints, LoadRobot)
├── state/
│   ├── mod.rs
│   └── robot.rs      # SceneRuntime, ActiveRobot
├── services/
│   ├── mod.rs
│   └── scene.rs      # SceneService (orquestador principal)
├── backends/
│   ├── mod.rs        # RobotBackend trait
│   └── internal.rs   # InternalBackend
└── snapshots/
    ├── mod.rs
    └── scene.rs      # RuntimeSnapshot

Reglas:

  • SceneService es el único punto de entrada para mutaciones del sistema.
  • Los Command son tipados e inmutables — representan intenciones.
  • Los RobotBackend siguen strategy pattern — el default es InternalBackend.
  • El runtime no sabe de HTTP — no importa nada de thalos-api.
  • SceneService::execute() siempre devuelve un RuntimeSnapshot completo.

9.3 Cómo agregar un modelo robótico nuevo

Agregar un robot concreto (ej: RRBot) requiere:

1. Crear la estructura de directorios

make robot NAME=rrbot
# Crea:
#   src/models/rrbot/
#   ├── mod.rs
#   ├── factory.rs
#   └── tests/
#       ├── mod.rs
#       └── fk.rs

2. Implementar la fábrica en factory.rs

use thalos_core::prelude::*;

pub fn create_rrbot(l1: f64, l2: f64) -> SerialChain {
    let mut builder = SerialChainBuilder::new();

    let base = builder.create_frame("base");
    let joint_1 = builder.create_frame("joint_1");
    let joint_2 = builder.create_frame("joint_2");
    let ee = builder.create_frame("ee");

    // ... configurar joints, links, segments ...

    builder.set_end_effector(ee);
    builder.build().expect("RRBot debe ser válido")
}

3. Agregar variante a RobotModel y RobotSpec

En models/factory.rs, agregar:

pub enum RobotModel {
    // ... existentes ...
    Rrbot,
}

pub enum RobotSpec {
    // ... existentes ...
    Rrbot { l1: f64, l2: f64 },
}

Y el match correspondiente en RobotRegistry::create().

4. Exportar la fábrica

En models/mod.rs:

pub mod factories {
    // ... existentes ...
    pub use crate::models::rrbot::factory::create_rrbot;
}

5. Escribir tests de FK

En tests/fk.rs:

#[cfg(test)]
mod rrbot_fk_tests {
    use thalos_core::prelude::*;

    #[test]
    fn test_home_position() {
        let robot = create_rrbot(1.0, 1.0);
        let fk = ForwardKinematics::new(robot);
        let result = fk.evaluate(&[0.0, 0.0]);

        let ee_pose = result.pose(
            &FrameId::Id(3) // ID del end-effector
        ).expect("end effector pose");

        // assert! ...
    }
}

9.4 Cómo agregar tests

9.4.1 Tests unitarios (en el mismo archivo)

#[cfg(test)]
mod vector3_tests {
    use super::*;

    #[test]
    fn test_magnitude() {
        let v = Vector3::new(3.0, 4.0, 0.0);
        assert!((v.magnitude() - 5.0).abs() < EPS);
    }
}

9.4.2 Tests de integración (en tests/)

Usar insta para snapshots cuando sea posible:

#[test]
fn test_planar_2r_scene() {
    let robot = RobotRegistry::create_default(RobotModel::Planar2R);
    let fk = ForwardKinematics::new(robot);
    let result = fk.evaluate(&[0.5, 0.3]);
    let scene = SceneBuilder::new(fk.robot()).from_fk(&result);
    insta::assert_json_snapshot!(scene);
}

Los snapshots permiten detectar visualmente cambios no deseados en CI sin abrir un visor 3D.

9.5 Qué evitar

9.5.1 No hacer

  • Importar thalos-visual, thalos-runtime o thalos-api desde thalos-core
  • Poner lógica de negocios en handlers HTTP
  • Usar unwrap() o expect() en código de producción (salvo en main.rs o tests)
  • Agregar dependencias pesadas al core (thalos-core solo debe tener nalgebra y thiserror)
  • Normalizaciones silenciosas — si una operación puede fallar, que retorne Result
  • Mezclar DTOs con tipos del dominio — los DTOs de API son independientes

9.5.2 Sí hacer

  • Validar invariantes en construcción (new() retorna Result)
  • Documentar el por qué de las decisiones (no solo el qué)
  • Mantener los tests al lado del código que testean
  • Usar thiserror para errores del dominio
  • Seguir la estructura de archivos establecida

9.6 Flujo de trabajo para contribuciones

  1. Leer la documentación de dominio y arquitectura
  2. Crear un issue o discussion describiendo el cambio
  3. Implementar siguiendo las convenciones del crate correspondiente
  4. Agregar tests (unitarios + integración con snapshot si aplica)
  5. Correr cargo test y cargo clippy
  6. Enviar PR con conventional commit
